1. Time budgets and where we stand

A show controller fails in two ways that matter: late (a cue starts after it should, a frame is dropped, audio clicks) and stuck (the operator presses GO and nothing happens). Every design choice below exists to keep one of these budgets:

2. The benchmark tool

The tool is src/bench.rs (library module), examples/bench.rs (CLI), tools/bench.sh (wrapper). ~30 s for a full run; all headless, no sound, fixed seeds.

# run, compare with the previous run and the previous version, update the history and this page
tools/bench.sh
tools/bench.sh --label "after fade rewrite" --tolerance 10

# or pin a reference run and compare with it (exit code 2 on a regression either way)
tools/bench.sh --set-baseline
tools/bench.sh --baseline

# quick look at a few groups (not comparable with full runs)
tools/bench.sh --quick --only engine,lookup
tools/bench.sh --no-realtime        # skip mixer + timing (the 15 s real-time groups)
GroupWhat it measuresWhy it's the right signal
enginetick p50/p99 with a 10k-cue list and 4 running; 2000 running at once; GO + tickthe 1 ms budget; scaling with show size and with activity
lookupfind, next_sibling, missing id, iter_allthe most frequent operation in engine and UI
mixeraudio-thread load and worst callback, 16/64/128 voices, with/without EQuses dsp_load() on the real mixer + decoders (virtual output)
timingstart error in samples for 32 chained cues while another thread holds the lock 0–12 ms; tick gapsend-to-end sample accuracy, the product promise
videoconversion + publish per frame: 1080p, 4K, 1080p with alphadecode-thread frame budget
textrender title / paragraphtime-to-first-display for unpreloaded text

workspacesave, load, file size, clone (5000 cues)save/autosave/undo costs
remotecue_patch, full snapshot serialisationper-edit cost with replicas
uiheadless frame time (20 / 3000 cues, two inspector tabs), engine's longest lock waitUI scaling and lock fairness

Reading the comparison: each metric shows old → new and the change; SLOWER means worse by more than the tolerance (default 15 %) and by more than a small absolute floor per unit (so 2 → 3 ns isn't "+50 %"). Worst-case metrics (p99, max, peak_, lock waits, tick gaps) are marked noisy: they print worse? (noisy) but never fail the run — re-run before trusting one. Results are kept in bench/results/ (git-ignored; numbers only compare on the same machine); the report records machine, profile, features and revision, and warns when two reports differ in those.

Not covered yet (needs hardware or a window): real device callback jitter, GPU upload/composite time (use tools/ui_perf.sh), real network replicas.

Results and history

Generated by tools/bench.sh: every complete run (no --quick, --only or --no-realtime) is compared with the previous run and with the last run of the previous OpenQ version, added to bench/history.json (one run per revision; a re-run replaces it) and this section is rebuilt from it. Only runs from the latest run's machine, profile and features are shown, since numbers from different machines don't compare. Lower is better everywhere.

3. Hardware requirements

What a computer needs for three kinds of show: audio only, audio + video (movies, stills, text, cameras on stage outputs) and audio + video + lighting (a DMX/Art-Net/sACN design on top). The figures come from the benchmark and the stress suite on the development machine (Ryzen 9 9950X3D, 32 threads, 30 GB, Linux, release build, 14 Oct 2026) and from the budgets in section 1. The minimums are worked out from those numbers (how much slower a CPU can be and still keep every budget with room to spare). OpenQ has not been run on minimum-spec hardware yet, and the macOS build has only been cross-compiled. Read the minimum table as "should work, test your show on it" and the recommended table as "what we would tour with".

What the figures are based on

MeasuredDev machineBudgetWhat it means for a slower computer
Engine tick, 2000 cues running at once (p99)≈ 0.6 ms1 msBig shows need a fast single core; a normal show (a few cues running) ticks in under 1 µs on any CPU.
Mixer, 64 voices with EQ (share of one core)≈ 6.5 %< 70 %A CPU 4× slower still has 3× headroom at 64 voices.
Video conversion, 1080p / 4K frame0.4 / 2.0 ms16.7 ms (60 fps)One decode thread per movie: several 4K movies at once want several fast cores.
UI frame, 3000 cues≈ 0.25 ms16.7 msAny CPU from the last ten years; the GPU matters more for stage outputs.
Lighting frame, 2000 fixtures, 28 universes, 3 sequences fading≈ 0.10 ms22.7 ms (44 Hz)Over 200× headroom: lighting is cheap.
Lighting frame, 9600 pixel cells, 60 universes, chases on every cell (p99)≈ 0.25 ms22.7 msThe light thread held 44 frames/s under GOs in the stress test.
Compiling a lighting design (2000 fixtures × 300 cues)≈ 185 msoff the hot pathRuns on a worker after an edit; a slow CPU only delays when an edit reaches the output.
Memory of the running app (empty show / lighting demo)≈ 200 MB—Plus media: decoded video frames, stills and text planes grow with the show.
Idle CPU with the window open≈ 1 % of one core—The UI repaints only when something changes.
